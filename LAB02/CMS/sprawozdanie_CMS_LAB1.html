2. Środowisko i repozytorium

Treści testowe dodaliśmy przez WP-CLI. Wpisy z wp post generate mają pusty tytuł, treść i autora, więc nadaliśmy im tytuły, kategorie (Poradniki, Nowości, Z palarni), treść, autora i różne daty publikacji. Bez różnych dat kolejność „3 ostatnich” była przypadkowa.

wp config set WP_DEBUG true --raw
wp config set WP_DEBUG_LOG true --raw
wp config set WP_DEBUG_DISPLAY true --raw
wp plugin install query-monitor --activate
wp theme activate kawanaklik
wp post generate --count=10
wp option update show_on_front page          # statyczna strona główna
wp menu location assign menu-glowne primary
wp menu location assign menu-w-stopce footer

Repozytorium zespołu = katalog wp-content. Każda osoba klonuje je do wp-content swojej strony w Local. .gitignore działa jak „biała lista”: wszystko jest domyślnie ignorowane, a do repozytorium trafia tylko nasz motyw i przyszłe własne wtyczki z prefiksem kawanaklik-. Nie wersjonujemy rdzenia WordPressa, wtyczek z katalogu, mediów (uploads/), cache ani logów.

3. Odpowiedzi na pytania

3.1. Który plik szablonu wybrał WordPress dla strony głównej, wpisu i nieistniejącego adresu?

Query Monitor (zakładka Template) pokazuje, który plik został użyty (Template File) i jakie pliki WordPress próbował znaleźć po kolei (Template Hierarchy). WordPress przechodzi listę od góry i bierze pierwszy plik, który istnieje w motywie.

AdresHierarchia sprawdzona przez WPUżyty plikDlaczego
Strona główna /front-page.php → page-strona-glowna.php → page-60.php → page.php → singular.php → index.phpfront-page.phpStrona główna ma ustawioną stałą stronę („Strona główna”, ID 60). front-page.php jest pierwszy w hierarchii i istnieje.
Wpis /?p=50single-post-post-2.php → single-post.php → single.php → singular.php → index.phpsingle.phpNie mamy szablonów dla konkretnego wpisu (slug) ani dla typu post, więc pierwszym istniejącym plikiem jest single.php.
Strona /o-nas/page-o-nas.php → page-62.php → page.php → singular.php → index.phppage.phpBrak szablonu dla sluga i ID tej strony, więc użyty jest ogólny page.php.

3.2. Czym różni się akcja od filtra? Przykłady z naszego kodu

Akcja (add_action) oznacza: „zrób coś w tym momencie”. Funkcja wykonuje operację (rejestruje, wypisuje, dołącza plik) i nic nie zwraca. Filtr (add_filter) oznacza: „dostajesz wartość, zmień ją i oddaj”. Funkcja musi zwrócić wartość, bo inaczej WordPress dostanie null i np. zajawka zniknie.

// inc/assets.php – AKCJA
function kawanaklik_assets(): void {
    $ver = wp_get_theme()->get( 'Version' );
    wp_enqueue_style( 'kawanaklik-main',
        get_theme_file_uri( 'assets/css/main.css' ),
        array(), $ver );
    wp_enqueue_script( 'kawanaklik-main',
        get_theme_file_uri( 'assets/js/main.js' ),
        array(), $ver, array( 'strategy' => 'defer' ) );
}
add_action( 'wp_enqueue_scripts', 'kawanaklik_assets' );
// inc/filters.php – FILTR
function kawanaklik_excerpt_length( int $length ): int {
    return 20;   // zamiast domyślnych 55 słów
}
add_filter( 'excerpt_length', 'kawanaklik_excerpt_length' );

function kawanaklik_excerpt_more( string $more ): string {
    return '…';  // zamiast „[…]”
}
add_filter( 'excerpt_more', 'kawanaklik_excerpt_more' );

Inne akcje w motywie: after_setup_theme (wsparcie funkcji i menu w inc/setup.php) i widgets_init (obszar „Stopka” w inc/widgets.php). Efekt filtra widać na rys. 4: zajawki mają 20 słów i kończą się wielokropkiem.

3.3. Co się stanie, jeśli w motywie zabraknie wp_head() lub wp_footer()?

Sprawdziliśmy to na kopii motywu na stronie: kolejno zakomentowaliśmy każde wywołanie, a potem przywróciliśmy oryginał.

Bez wp_head():

  • Znika wszystko, co WordPress i wtyczki dodają w <head>. Nie ładuje się main.css, więc strona wraca do surowego HTML. Element <title> jest pusty, bo title-tag generuje go właśnie w wp_head.
  • Brakuje też meta (np. robots), styli WooCommerce i stylu przesunięcia pod pasek admina. Pasek admina co prawda się wyświetla (WordPress dokleja jego style później, w stopce), ale zasłania początek strony.
  • Pomiar w konsoli: main.css = brak, document.title = "".

Bez wp_footer():

  • Wygląd strony się nie zmienia, bo CSS i nasz skrypt z defer są w <head>. Nie ładują się jednak skrypty kolejkowane do stopki. Liczba skryptów na stronie spadła z 22 do 10.
  • Zniknęły: admin-bar.js i hoverintent (obsługa pasków admina), emoji, skrypty WooCommerce sourcebuster i order-attribution oraz cały Query Monitor. W pasku widać tylko napis „Query Monitor” bez statystyk, a panelu nie da się otworzyć.
  • W nowszych wersjach WordPressa sam pasek admina jest wypisywany już w wp_body_open(), więc nie znika całkowicie. Traci jednak skrypty, a wtyczki zależne od stopki (formularze, statystyki, koszyk WooCommerce) mogą przestać działać.

Wniosek: oba wywołania są obowiązkowe. To punkty zaczepienia, przez które rdzeń i każda wtyczka dokładają swoje zasoby do strony.

3.4. Po co jest wp_reset_postdata()? Co się dzieje bez tego wywołania?

Metoda the_post() własnego WP_Query nadpisuje globalną zmienną $post i dane bieżącego wpisu. Po pętli $post wskazuje więc na ostatni wpis z pętli, a nie na stronę, którą wyświetlamy. wp_reset_postdata() przywraca $post z głównego zapytania. Dzięki temu funkcje wywołane później (the_title(), get_the_ID(), warunki, pola ACF, widgety) dotyczą właściwej strony.

W front-page.php pod listą wpisów wyświetlamy dopisek get_the_title():

  • z wp_reset_postdata(): „Jesteś na stronie: Strona główna” – poprawnie,
  • bez wp_reset_postdata(): „Jesteś na stronie: Co oznacza data palenia na opakowaniu”, czyli tytuł trzeciego, ostatniego wpisu z pętli.

Na zajęciach z ACF taki błąd oznaczałby, że get_field() czyta pola niewłaściwego wpisu.

6. Wnioski

  • Hierarchia szablonów pozwala zacząć od samego index.php i dodawać bardziej szczegółowe pliki tylko tam, gdzie widok ma wyglądać inaczej. Query Monitor pokazuje dokładnie, który plik wygrał.
  • Motyw komunikuje się z rdzeniem i wtyczkami wyłącznie przez hooki. Wywołania wp_head(), wp_body_open() i wp_footer() to obowiązkowe „gniazda” dla cudzego kodu.
  • Każde własne WP_Query trzeba zamknąć wp_reset_postdata(). Inaczej dalsza część szablonu działa na niewłaściwym wpisie.
  • WP_DEBUG pomaga wykryć nie tylko błędy motywu, ale też ostrzeżenia z innych komponentów, jak strona „Wkrótce” WooCommerce. Warto sprawdzać stronę także jako niezalogowany gość.
